### How the frontend communicates with the backend

- In **development**: Vite proxies all `/api/*` requests from `http://127.0.0.1:5173` to `http://127.0.0.1:5001`. The frontend code uses relative paths (e.g. `/api/build-kb`) with no hardcoded backend URL.
- In **production**: The Vite proxy does not exist. The frontend build is static HTML/CSS/JS. For production, the frontend must either be served from the same origin as the backend, or a `VITE_API_BASE_URL` environment variable must be injected at build time so the frontend knows where the backend lives. **This wiring is the main change required for deployment.**

### Vite proxy configuration (`vite.config.ts`)

```ts
proxy: {
  "/api": {
    target: "http://127.0.0.1:5001",
    changeOrigin: true,
    secure: false,
  },
},
```

### All API routes (`server.js`)

| Method | Route | Purpose | External APIs |
|--------|-------|---------|---------------|
| `POST` | `/api/build-kb` | Scrapes a website URL via Firecrawl, extracts service offers + benefits via Gemini structured output, merges with fallback CSV data. Returns `{ offers, subOffers, benefitsByOffer }`. | Firecrawl, Gemini |
| `POST` | `/api/refine-instruction` | Takes a current prompt and a user refinement instruction. Returns an updated prompt string. Has a simple in-memory rate limiter (429 on abuse). | Gemini |
| `GET`  | `/api/health` | Health check. Returns `{ ok: true }`. | None |

2. Open `http://127.0.0.1:5173/`.
3. Enter a business website URL, select a business type (e.g. "Japanese Restaurant"), enter a company name.

7. Optionally open the palette slide-out and pick a colour.
8. Click **Generate Prompt** — assembled image-generation prompt appears in the right column.

## 6. Deployment Considerations

### Long-running API calls

The `/api/build-kb` route is the slowest call in the app. It runs:
1. A Firecrawl scrape with `waitFor: 3000` and `timeout: 30000` (30 seconds per tier, up to 3 tiers).
2. Multiple sequential Gemini calls for offer extraction and per-offer benefit generation.

**Total wall-clock time for `/api/build-kb` can reach 30–90 seconds** in worst-case scenarios (slow site + AI retries). This will exceed the default 10-second timeout on Vercel Serverless Functions. Codex must evaluate whether to use Vercel Functions with `maxDuration` set to 300s (Pro plan required), use a long-running platform (Railway, Render, Fly.io), or restructure the pipeline into streaming or queued steps.

### Payload sizes

- `express.json({ limit: "2mb" })` — request body limit is 2 MB.
- `fallback-services.json` is read from disk at request time. It must be present in the deployment filesystem (not suitable for edge functions without bundling).

### In-memory rate limiter

`/api/refine-instruction` has a simple in-memory rate limiter (Map-based, keyed by IP). This state is lost on process restart and will not work correctly across multiple serverless instances. Codex should be aware of this if deploying to a multi-instance environment.

### Serverless hosting compatibility summary

| Concern | Detail |
|---------|--------|
| Execution timeout | `/api/build-kb` can take 30–90s. Default Vercel limit is 10s. |
| Filesystem reads | `fallback-services.json` must be bundled or available at runtime. |
| In-memory state | Rate limiter in `/api/refine-instruction` will not persist across cold starts. |
| Binding | `server.js` currently binds to `127.0.0.1` — must be changed for any hosted environment. |
| CORS | Currently wide open — must be restricted to the deployed frontend origin. |

**Codex must inspect the project and determine whether a single Vercel deployment is suitable, or whether a separate long-running backend host is required.**
